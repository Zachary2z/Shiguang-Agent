| 文档信息 | 内容 |
|---|---|
| 文档状态 | 需求确认稿 |
| 产品阶段 | 个人作品集项目 / 小范围体验验证 |

| 文档日期 | 2026-07-20 |

> 一句话定义：用户把“以后想去、想做、想吃”的地点或活动发给拾光；当用户真正有空时，Agent 结合收藏、时间、位置、天气和路线，把兴趣整理成一份可以执行的同城计划。

## 1. 文档目的

本文档从产品视角定义“拾光”的用户价值、目标用户、双端体验、Agent 权限、MVP 范围、数据规则、技术依赖、验证方式与交付标准，作为产品设计、开发、测试和作品集展示的共同依据。

本版重点回答：

1. 用户为什么需要拾光，它解决了收藏后的哪个断点？
2. 用户在微信和 Web/H5 中如何完成收藏、规划、确认与反馈？
3. Agent 如何使用用户数据和外部工具，又如何避免越权与编造？
4. 个人开发者应先做什么，哪些能力延后？
5. 在无法招募大量内测用户时，如何诚实验证项目价值？

## 2. 产品概述

### 2.1 产品背景

用户会在小红书、公众号、视频号、朋友圈和网页中遇到大量感兴趣的地点与活动，但收藏通常存在三个断点：

- **信息分散**：内容散落在多个平台，难以统一查找和整理。
- **缺少现实约束**：原收藏不知道用户什么时候有空、从哪里出发、和谁同行，也不会核验天气、营业状态和路线。
- **缺少行动闭环**：用户还要重新筛选、查询、组合和安排，最终大量收藏长期积灰。

传统收藏工具主要解决“存下来”，通用聊天机器人主要解决“问一次、答一次”。拾光进一步解决的是“在什么条件下值得去，以及怎样把它真正安排下来”。

### 2.2 产品愿景

让每一次“这个不错，先收藏”都更接近一次真实发生的生活体验。

### 2.3 产品定位

拾光是一款面向个人用户的轻量同城生活规划 Agent。它不是内容社区、旅游攻略平台或自动代订服务，而是连接用户已有兴趣与现实约束的行动中枢。

拾光不以生成公共热门攻略为核心，也不与地图平台竞争 POI、评价、路线和导航覆盖。它优先使用用户已经收藏的内容，根据用户本次真正可用的时间和活动范围，完成候选选择、计划组合、用户确认与行动协助。

### 2.4 核心价值

| 用户问题 | 产品能力 | 用户价值 |
|---|---|---|
| 收藏分散、回看困难 | 多来源导入与统一结构化收藏 | 降低整理成本 |
| 有空时不知道做什么 | 根据收藏与临时条件生成计划 | 降低决策成本 |
| 攻略可能过期 | 规划时核验地点、天气和路线 | 提高可执行性 |
| Agent 容易误解用户 | 透明、可修改、可删除的记忆 | 提升控制感与信任 |
| 计划生成后仍不行动 | 路线、日历、提醒和反馈闭环 | 推动收藏转化为行动 |

### 2.5 核心闭环

**发现内容 → 发给拾光 → 自动结构化收藏 → 用户修改/撤销 → 提供空闲时间与范围 → Agent 生成计划 → 用户调整并确认 → 日历/路线/提醒 → 反馈与状态更新**

## 3. 产品目标与非目标

### 3.1 MVP 目标

1. 用户可以通过自然语言、文本 URL 或截图快速保存一个地点或活动。
2. 系统能够提取标题、地点、时间、价格、标签、来源与不确定项，并允许用户修改或撤销。
3. 用户提供空闲时间和活动范围后，系统能从其收藏出发生成一份深圳半日或一日计划；其他城市收藏暂不进入当前 MVP 的计划。
4. 计划能够展示费用、交通、天气、信息来源、风险和候选排除原因。
5. 所有长期记忆、主动提醒和外部写操作都遵守明确的授权规则。
6. Web/H5 能作为可公开分享的作品集 Demo，展示完整体验与 Agent 工作轨迹。

### 3.2 非目标

MVP 不实现：

- 用户内容社区、关注关系、达人体系或推荐信息流；
- 运行时计划城市切换、多城市联合规划或跨城规划；MVP 允许跨城市收藏，但始终以深圳完成单城市计划闭环；
- 跨城、多日行程、机票酒店与复杂旅游规划；
- 自动付款、下单、购票、订座或代替用户发送社交消息；
- 登录第三方内容平台、批量搬运收藏或绕过平台访问限制；
- 对转发的公众号卡片、小程序卡片提供稳定解析承诺；
- 原生 iOS/Android App；
- 自研大模型或以复杂多 Agent 编排作为产品卖点；
- 未经确认修改外部系统或生成不可逆结果。

### 3.3 商业模式边界

当前项目定位为个人作品集，不开发支付、会员、广告、返佣或商家推广能力。PRD 仅保留未来“免费基础功能 + 订阅高级规划”的商业假设，不将其作为当前成功标准。

### 3.4 跨城市收藏与后续计划城市扩展

跨城市收藏属于当前基础能力，不等同于运行时城市切换：用户可以先记录任何城市的 Place 或主动提供的 Event，收藏流程不得仅因地点不在深圳而拒绝。当前 MVP 的计划生成、外部补充和公开 Demo 仍只启用深圳，其他城市收藏保留在收藏库中，供城市筛选、后续补充位置或未来计划城市开放后使用。

当前版本必须遵守：

- 收藏城市线索与本次计划城市分离；地点或活动标题中的城市词不能自动成为已确认城市；
- 原文明确给出的城市只作为 `city_hint`，只有 POI 匹配或用户确认后才形成可用于规划的正式城市；
- 收藏库支持按城市查看和筛选，并提供“城市待确认”分类；相关界面布局在后续前端阶段设计；
- 当前深圳计划只读取位置已确认、状态有效且正式城市属于深圳的收藏；其他城市收藏不会被删除、迁移或误纳入计划；
- 一条输入可以抽取不同城市的多个收藏候选；跨城多日行程规划仍是不支持的另一类意图。

运行时计划城市切换仍作为深圳闭环稳定后的候选升级点。升级时区分用户默认城市、Session 当前计划城市、收藏城市线索/正式城市和 Plan 城市；城市切换必须由用户明确触发，一份计划仍只有一个城市，跨城、多日行程继续单独评估。

## 4. 目标用户

### 4.1 核心用户

- 生活在深圳、习惯收藏线下地点或活动的在校大学生与年轻职场人；
- 经常从内容平台保存餐厅、咖啡店、展览、市集、公园等信息；
- 有兴趣但时间有限，常因重新搜索、选择和安排成本过高而不行动；
- 习惯微信沟通，愿意用自然语言表达临时需求；
- 接受 AI 建议，但希望知道建议依据并保留最终决定权。

### 4.2 用户定位原则

产品不按“学生/职场人”设计两套流程，也不要求读取课程表或工作日历。用户只需要告诉 Agent 本次真正可用的：

- 空闲时间；
- 活动范围或出发区域；
- 同行人和特殊要求；
- 预算（可选）。

职业和课程不是规划的必填条件，选择权交给用户。

### 4.3 非核心用户

- 需要多人协同审批、企业差旅或团队活动管理的 B 端用户；
- 需要跨城多日、机酒联动和精细预算的重度旅行用户；
- 完全不愿提供任何时间、位置范围或兴趣数据的用户。

### 4.4 典型用户画像

**林晓，24 岁，居住在深圳南山区**

- 可能是在校研究生，也可能是刚工作的产品新人；职业身份不影响使用流程。
- 平时收藏展览、咖啡店、公园和周末市集，内容分散在多个平台。
- 周末活动时间不固定，有时独自出门，有时与朋友同行。
- 通常乘坐地铁，不愿为了维护收藏再填写复杂表格。
- 希望系统提供一份主方案，同时告诉她费用、路线和可能踩坑的地方。

## 5. 用户需求与核心场景

### 5.1 Jobs To Be Done

当我看到感兴趣的线下地点或活动时，我希望不用整理就能先交给一个助手；当我真正有空时，它能结合我这次的现实条件，把已有兴趣组合成一份可执行方案，让我不必重新搜索和反复决策。

### 5.2 核心场景

1. **随手收藏**：用户把文本 URL、截图或一段文字发给 Agent，系统自动识别并保存。
2. **收藏修改**：用户通过 Web 按钮或微信自然语言修正字段，也可以撤销刚才的收藏。
3. **即时检索**：用户询问“我收藏过适合雨天、南山附近的地方吗？”
4. **按需规划**：用户告诉 Agent 空闲时间和活动范围，由 Agent 生成计划。
5. **主动询问**：用户开启后，Agent 每周四询问周末是否有空，不擅自生成或确认计划。
6. **临时调整**：用户补充“晚两小时”“不要日料”“少走一点”，Agent 保留其他条件重新计算。
7. **执行协助**：确认计划后生成 `.ics` 文件、高德路线入口和可选提醒。
8. **反馈学习**：活动结束后，用户可反馈完成情况和原因；长期偏好必须再次确认。

## 6. 产品原则

1. **收藏驱动**：优先使用用户已有收藏；仅在候选不足时补充外部建议。
2. **用户提供现实条件**：不猜测课程、工作安排和预算。
3. **事实靠工具，偏好靠记忆**：天气、营业状态和路线必须实时查询，不能写入长期记忆。
4. **确定性任务优先用规则**：模型负责理解，数据库和业务规则负责可靠执行。
5. **内部可逆动作可自动，重要动作必须确认**：保存草稿可以撤销；长期记忆、主动提醒和外部写操作必须授权。
6. **不确定就明确表达**：信息缺失、冲突或接口失败时标注“待确认”，不得编造。
7. **对话低门槛，界面可管理**：微信完成快速输入，Web/H5 承担完整编辑、管理和展示。
8. **单一数据模型**：微信与 Web 共用同一套字段、业务规则和 API。
9. **解释到决策层**：展示约束、来源、工具和取舍，不暴露内部思维链。

## 7. 产品形态与渠道策略

### 7.1 双端定位

| 端 | 角色 | 首期能力 |
|---|---|---|
| 微信 ClawBot | 高频输入与轻量对话入口 | 发文字、链接和截图；自然语言修改；计划确认；提醒与反馈 |
| Web/H5 | 控制中心与作品集 Demo | 收藏管理、计划比较、记忆中心、授权记录、Agent 轨迹、公开演示 |

### 7.2 开发顺序

先完成共享核心与 Web/H5，再接入微信。两端始终调用同一套 FastAPI、Agent、数据库和工具，不建立两套业务逻辑。

### 7.3 微信接入规则

- 微信使用腾讯官方 ClawBot/OpenClaw 微信插件作为消息通道。
- 官方插件原生面向 OpenClaw，因此 M2 增加 Channel Adapter，将微信消息转换为 Nanobot 的统一消息格式。
- 文本粘贴的 URL、普通文字和截图作为 P0 输入。
- 直接转发的公众号卡片、小程序卡片、语音、视频、批量导入和平台账号登录不作为 P0 承诺。
- 链接解析失败时只自动重试一次，随后立即请求用户发送截图或补充文字。
- 当前微信消息协议不依赖原生交互按钮：简单选择使用数字回复，自由修改使用自然语言，复杂编辑跳转 H5。
- ClawBot 更适合个人或小范围体验，不将其假设为可通过一个公开链接直接服务所有用户的公众机器人。
- 主动消息失败时保留 Web/H5 待办，不虚假显示“已送达”。

### 7.4 Web/H5 信息架构

Web/H5 默认进入 **Agent**，不以地图、公共推荐信息流或传统数据看板作为首页。移动端采用四项底部导航，桌面端使用语义一致的侧边导航：

1. **Agent**：默认首页；发送文字、文本 URL 和截图，发起收藏、检索、规划、修改与确认；首页主输入提示为“把想去的地方发给我，或者告诉我你什么时候有空”；
2. **收藏**：卡片/列表、搜索、筛选、待确认处理、详情编辑、状态管理和删除；
3. **计划**：计划草案、主方案与备选、冲突说明、版本、确认状态、历史记录和执行入口；
4. **我的**：记忆中心、主动计划与提醒授权、数据导出、账号绑定和注销设置。

Agent 运行记录不占用一级导航：真实用户在计划或消息详情中按需展开本次使用的信息、工具、结果与授权；公开作品集 Demo 可以提供独立的“查看 Agent 工作过程”入口。

复杂修改从对话卡片进入收藏详情、计划详情或编辑页；完成后返回原对话上下文。Web/H5 与微信使用同一业务数据和动作，只改变呈现方式。

### 7.5 低保真原型范围

原型采用移动端 H5 优先，建议基准画布宽度为 390px；桌面端首轮只覆盖作品集展示所需关键页面。低保真阶段验证任务、信息层级、状态与跳转，不提前投入完整视觉规范和高保真动效。

首批 8 个移动端页面：

1. Agent 首页；
2. Agent 对话与收藏结果；
3. 收藏库；
4. 收藏详情与地点消歧；
5. 计划草案；
6. 已确认计划与执行入口；
7. “我的”及记忆/提醒/设备设置；
8. 脱敏的只读计划分享页。

首批 2 个桌面端页面：

1. 作品集介绍与公开 Demo 入口；
2. 桌面版 Agent + 计划详情组合页面。

高德外部检索授权、空结果、工具失败、部分完成反馈、Agent 工作过程和删除/撤销确认作为上述页面的状态、抽屉或弹层处理，不额外增加一级页面。

产出顺序：核心用户流程图 → 10 个低保真页面 → 可点击核心链路 → 视觉方向与高保真设计。

## 8. 账号、Demo 与首次使用

### 8.1 账号模式

| 模式 | 身份方式 | 数据 |
|---|---|---|
| 公开 Demo | 无需登录，浏览器临时会话 | 深圳虚拟用户与可重置沙盒数据 |
| 真实用户 | ClawBot 用户通过一次性签名链接或绑定码关联 Web | 用户自己的收藏、计划和记忆 |

MVP 不开发手机号注册、密码登录和微信网页 OAuth。

#### 8.1.1 微信到 Web/H5 的一次性登录流程

1. 用户在微信中请求“打开网页版”，或点击收藏/计划消息中的“查看详情”；
2. 服务端为当前微信用户生成与目标页面关联的一次性私人登录链接。链接默认 10 分钟内有效且只能成功使用一次；
3. H5 打开链接后，将一次性凭证兑换为服务端登录会话，再跳转至对应收藏、计划或 Agent 上下文；URL 中的一次性凭证不得继续作为长期会话凭证；
4. 网页登录状态默认保留 30 天。用户可以在“我的—登录设备”中退出当前设备或撤销全部网页会话；
5. 链接过期、已使用或已撤销时不得访问个人数据，只提示用户回到微信重新获取；
6. 微信与 Web/H5 关联同一内部 `user_id`，收藏、计划、记忆、授权和修改结果使用同一份数据；
7. 私人登录链接与计划分享链接使用不同的令牌类型、访问路由和权限范围，不得互相兑换；
8. 私人登录链接可访问当前用户数据，必须短时、单次有效；计划分享链接只能读取用户明确分享的单份计划，不具备登录能力。

### 8.2 渐进式引导

首次使用只完成三件事：

1. 说明产品价值、数据用途与删除方式；
2. 告知当前计划城市为深圳，同时可以先收藏其他城市内容；
3. 邀请用户发送第一条链接、截图或文字。

不要求用户在首次进入时填写年龄、职业、预算、精确住址、课程表或完整兴趣。交通方式、同行人、空闲时间和长期偏好在实际需要时再询问。

### 8.3 首次价值标准

新用户应在 3 分钟内完成一次收藏，并看到：

- 系统识别出的地点或活动；
- 已确认信息和待确认信息；
- “修改”和“撤销”的下一步；
- 该收藏未来可用于哪类计划。

### 8.4 冷启动与首次计划

产品同时区分“首次收藏价值”和“首次计划价值”，避免用户只保存一条内容后仍无法体验核心闭环。

- 完成第 1 条有效收藏后，立即展示结构化结果、地点匹配状态、修改/撤销入口和可用的单点行动信息；
- 累积 3 条有效、已定位的可规划收藏后，主动邀请用户体验第一次完整计划；
- 3 条不是发起计划的硬门槛：收藏不足时，用户仍可生成单点出行建议或较简单的计划；
- 候选不足以形成完整方案时，Agent 提供明确选择：继续添加收藏、使用高德补充且已标记的外部 Place、只安排现有收藏；MVP 不自动补充外部 Event；
- 公开 Demo 预置足够的深圳虚拟收藏，访客无需先录入大量内容即可体验计划闭环；
- 首次收藏完成时间和首次计划完成时间分别记录，不用单一激活指标混在一起。

### 8.5 公开作品集 Demo

公开 Demo 采用无需登录的深圳引导式沙盒，与真实用户数据、私人登录链接和真实计划分享链接完全隔离。作品集首页提供“立即体验”和“查看完整案例”两个入口。

#### 8.5.1 预置数据与引导

- 每个匿名会话预置约 8–10 条深圳虚拟收藏，覆盖美术馆、博物馆、公园、咖啡店、餐厅、有效 Event、已过期 Event、待选择分店和信息不完整收藏；
- 提供内置文字、链接结果和截图样例，访客无需先录入大量内容即可体验收藏、消歧和规划；
- 页面明确说明当前使用虚拟数据，并区分实时查询结果与演示缓存结果。

#### 8.5.2 允许体验的能力

- 使用内置样例完成收藏、修改、撤销和同名分店选择；
- 查看收藏库，输入空闲时间和活动范围，生成、调整和确认计划；
- 区分个人收藏与高德补充 Place，下载演示 `.ics`，打开高德路线；
- 手动标记已完成、部分完成或未完成；
- 展开“Agent 工作过程”，查看意图解析、收藏查询、天气/路线核验、外部补充、计划生成等步骤的工具状态、来源、耗时和降级结果；
- Agent 工作过程不展示模型思维链、系统提示词、密钥或隐私参数。

#### 8.5.3 首个公开版本的限制

- 不开放任意网址抓取、访客私人图片上传、真实微信绑定、主动提醒、外部消息、永久数据保存、真实用户数据访问、自动购票或预订；
- 每个匿名会话最多执行约 10 轮 Agent 操作；高德、天气和路线优先使用深圳预置缓存；
- 对 IP 和匿名会话执行频率限制。达到限制后允许继续浏览已有结果，但不再调用模型或外部工具；
- 沙盒数据默认保留 2 小时，并提供“重新开始 Demo”入口；到期后自动删除匿名会话数据；
- 产品统计只记录必要的匿名事件与结果状态，不记录访客输入正文。

## 9. 内容导入与收藏模型

### 9.1 支持的内容类型

MVP 只将以下两类内容转成可规划收藏：

- **Place**：餐厅、咖啡店、美术馆、博物馆、公园、商场等相对稳定的地点；
- **Event**：展览、市集、演出、讲座等具有开始/结束时间的活动。

商品、菜谱、跨城多日旅行请求、复杂户外路线等内容可以识别为“不在当前规划范围”，但其他城市的单个地点、活动或多条收藏请求仍可进入收藏流程。

### 9.2 输入类型

- P0：普通文字、文本 URL、图片/截图；
- 后续：语音转写、更多文件类型；
- 不承诺：登录后页面、受限卡片、批量导入和自动读取平台收藏夹。

### 9.3 来源兼容与降级矩阵

| 来源 | MVP 处理方式 | 失败后的最短路径 |
|---|---|---|
| 普通公开网页 | 直接获取正文与元数据并解析 | 保存 URL，请用户补充文字或截图 |
| 公开短链接 | 跟随安全重定向后解析最终页面 | 保存原始与最终 URL，转截图 |
| 小红书公开文本 URL | 尝试解析一次，不承诺稳定成功 | 保存 URL，请用户发送包含店名/活动信息的截图 |
| 公众号文章公开 URL | 仅在页面可公开访问时解析 | 页面受限时请求截图 |
| 公众号/小程序卡片 | P0 不承诺直接接收或解析 | 用户发送截图或复制公开链接 |
| 大众点评等受限页面 | URL 只作为来源，能读则解析 | 使用截图和用户补充信息 |
| 高德/腾讯地图分享链接 | P0 保存来源并识别可获得的地点信息；完整快速导入列为后续 | 请求店名、区域或地图截图 |

业务规则：

- 同一输入最多自动重试一次，不能访问时立即进入截图兜底；
- 解析成功率必须按来源平台分别统计，不能只报告一个总体成功率；
- 50 条内容解析评测集应覆盖上述主要来源，并记录“直接成功、截图后成功、最终失败”；
- 不绕过登录、验证码、付费墙或平台访问控制。

### 9.4 核心字段

- 基础信息：标题、类型、城市线索、已确认城市、行政区、地址、经纬度、地图供应商与 POI ID；
- 活动信息：开放/活动时间、预计时长、价格或人均、预约方式；
- 场景标签：室内/室外、独处/约会/朋友、雨天适用、交通特征；
- 来源信息：原始 URL、平台、抓取时间、截图、字段来源；
- 质量信息：字段置信度、过期风险、最后核验时间和缺失项；
- 状态信息：想去、已计划、去过、已过期、已归档、回收站。

### 9.5 自动保存与修改

用户主动发送链接、截图或地点描述，默认视为“希望收藏”。系统完成轻量解析后自动保存，并立即提供可逆操作：

> 已收藏“深圳当代艺术与城市规划馆”。识别到：福田区、免费、室内；周一闭馆信息待规划前复核。回复“修改”或“撤销”即可调整。

- Web/H5 显示“修改”“撤销”按钮；
- 微信显示数字选项或提示用户直接说出修改内容；
- 简单修改示例：“区域改成福田区”“价格改为免费”；
- 复杂修改进入 H5 完整表单；
- 撤销仅影响本次收藏，不删除其他来源或同一 POI 的历史记录。

#### 9.5.1 首次输入到收藏的状态流程

1. 用户发送普通文字、文本 URL 或截图后，界面立即创建本次导入任务并显示“正在识别”，避免重复提交；此时尚不向用户宣称收藏成功；
2. Agent 完成内容解析与必要的高德 POI 匹配后，进入以下四种结果之一：

| 结果 | 用户提示 | 数据处理 | 下一步 |
|---|---|---|---|
| 唯一高置信地点/活动 | 已收藏 | 自动创建有效收藏，展示结构化卡片 | 修改、撤销、查看收藏、继续添加 |
| 存在多个合理地点或分店 | 已记录，待选择位置 | 创建“待选择”收藏，不关联不确定 POI | 展示最多 3 个候选供用户选择 |
| 信息不足但能识别标题或对象 | 已记录，待补充 | 创建“待补充”收藏，保留来源和已识别字段 | 只询问区域、商圈、地标等最少信息 |
| 无法识别或内容类型不在产品范围 | 未收藏，并说明原因 | 不创建收藏；保留本次导入结果用于错误恢复与观测 | 建议补充文字、发送截图或改用受支持内容 |

3. “待选择”和“待补充”内容在收藏库中集中展示，但不得进入路线计算或正式计划；
4. Web/H5 使用状态卡片和按钮，微信使用简短消息、数字选项与自然语言；两端共享相同状态和业务动作；
5. 收藏成功后的首要操作为“继续添加”和“查看收藏”，不强迫只有一条收藏的新用户立即发起完整计划。

### 9.6 多条内容与去重

- 一个来源包含多个地点/活动时，先列出候选，由用户选择后分别创建收藏；它们共享来源记录。
- 相同 URL 默认判定为重复，不创建第二条。
- 相同高德 POI ID 合并为同一地点，但可保留多个来源。
- 仅名称相似时必须询问用户，不能自动合并。
- “去过”条目可以重新标记为“想再去”。

### 9.7 仅店名输入的 POI 匹配与消歧

当帖子、截图或文字只识别出店名时，系统不得从名称中的城市词推断实际城市。原文有明确城市线索时在该城市范围内搜索；没有城市线索时，当前 MVP 可以深圳作为默认搜索范围，但必须保持城市待确认，不能保证仅凭名称定位准确地点。

系统应同时利用来源中可获得的辅助线索进行匹配，包括分店名、行政区、商圈、附近地标、地铁站、电话号码、地点类型、图片定位标签和原文上下文。

| 匹配状态 | 判定 | 系统行为 |
|---|---|---|
| 已匹配 | 某一城市范围内存在唯一高置信候选，名称和辅助线索一致 | 关联 POI ID 和正式城市，展示完整名称与地址，并允许用户纠正 |
| 待选择 | 存在多个合理候选或连锁分店 | 展示最多 3 个候选；微信使用数字回复，Web 使用地点卡片 |
| 待补充 | 无可靠候选、店名过于通用或地图尚未收录 | 保存店名，请求区域、商圈、地标、帖子链接或地图链接 |

业务规则：

- “排名第一”不等于“位置已确认”，低置信结果不得自动关联；
- 用户纠正后保存其选择和确认来源，避免下次重复询问；
- 处于“待选择”或“待补充”的收藏可以留在收藏库，但不得参与路线计算和正式计划；
- 规划时若收藏仍未定位，Agent 应说明原因，并提供补充位置或暂时排除该条目的选择；
- 连锁店不同分店视为不同 POI，不得只按品牌名去重。

#### 9.7.1 连锁品牌的“任意分店”收藏

当用户明确表达“这家店任意分店都可以”“先记住这个品牌，之后选附近的店”时，这不是尚未完成的地点消歧，而是用户确认的灵活地点策略：

- 系统只创建一条品牌级 Place 收藏，不为搜索到的每个分店自动创建收藏；
- 收藏状态为有效，但地点范围标记为“任意分店”，与“待选择”状态明确区分；
- 最多 3 个高相关分店只作为可刷新候选或缓存，不等于 3 条正式收藏，也不代表完整分店清单；
- 用户明确选择多个具体分店时，才为每个分店分别创建收藏；这些收藏共享来源，但状态、地址、POI ID 和到访记录独立；
- 规划时根据本次活动区域、路线和时间重新查找或刷新分店，并把本次采用的具体分店写入 PlanItem 快照；品牌级收藏本身不永久改绑到该分店；
- 本次计划选中的分店属于“收藏解析结果”，不标记为“外部补充 · 未收藏”；
- 到访记录绑定实际分店，品牌级收藏默认继续有效，直到用户明确归档或删除；
- 匹配证据不足、高德失败或没有满足硬约束的分店时，不得自动选择，必须说明原因并提供补充区域、选择分店或暂时排除。

## 10. 计划生成

### 10.1 规划范围

- 首发计划城市仅深圳；收藏库本身允许保留其他城市内容；
- 单次计划只处理同城、一个连续空闲时间段；
- 计划长度不超过一天；
- 不处理跨城、多日、酒店、机票和复杂预约链路。

### 10.2 用户输入

每次规划只要求：

1. 空闲时间段；
2. 活动范围或出发区域。

以下信息可选：同行人、交通偏好、特殊要求和预算。

- 用户提供预算时，它是硬约束；
- 用户不提供预算时，不按价格过滤，但必须显示每项和总费用估算；
- 无法确认费用时标注“价格待确认”，由用户自行判断。

### 10.3 候选来源

1. 首先从用户收藏中检索符合条件的 Place/Event；
2. 收藏中的 Place 不足或全部违反约束时，才允许调用高德 POI 搜索补充外部 Place；
3. Agent 将用户偏好转换为城市、区域、中心点、半径、POI 类型和关键词等查询条件，再结合距离、路线、预算信息完整度与当前行程进行二次排序；高德只提供地点候选，不承担个性化偏好理解；
4. 外部 Place 必须标注“来自高德外部补充”，并说明补充原因和仍待用户确认的信息；
5. 外部 Place 不会自动进入收藏库，用户明确保存后才写入；
6. MVP 不自动从外部检索 Event。展览、市集、演出、讲座等动态活动只使用用户主动提交并已保存的内容；不足时提示用户继续添加收藏或仅使用现有内容生成计划；
7. 后续仅在确定稳定、合规的数据来源后，才接入活动平台或场馆官方数据源。

#### 10.3.1 “收藏不足”的判断与外部检索触发

“收藏不足”不按收藏总数或固定条数判断，而是判断过滤硬约束后，现有收藏能否组成满足本次需求的可执行方案。

1. **现有收藏可以形成可执行计划**：只使用收藏，不调用高德补充；
2. **已有核心收藏，但存在明显行程空缺**：例如缺少就餐、休息等地点，或存在无法合理安排的较长空档。Agent 可以自动进行一次只读高德检索，补充少量外部 Place，并在草案中明确标注来源；
3. **没有任何符合条件的收藏，或计划将主要由外部地点构成**：Agent 必须先询问用户是否允许使用高德推荐，获得同意后再检索；
4. **用户明确要求某类 Event，但收藏中没有有效候选**：MVP 不自动外部检索，也不把美术馆、剧院等 Place 推断为正在举行的活动；提示用户发送活动链接/截图，或询问是否改为规划相应类型的固定地点；
5. **用户明确限制来源或类别**：支持“只用我的收藏”“可以补充外部地点”“不要推荐餐厅”等临时约束，并在本次规划全程保留。

核心规则：能用收藏完成时不外搜；只缺少局部环节时允许自动只读补充 Place；计划将主要依赖外部地点时先征得用户同意。

### 10.4 约束与排序

**硬约束**：用户不可用时间、活动已结束、地点不在深圳、POI 仍处于“待选择/待补充”、无法在时间内到达，以及用户明确设置的预算上限。违反任一项即淘汰或请求放宽。

**软偏好**：兴趣、距离、天气适配、排队风险、新鲜感、室内/室外、交通舒适度等。软偏好只影响排序，不能伪装成硬限制。

#### 10.4.1 计划密度与留白

- 用户提供的空闲时间是本次规划的可用上限，不代表计划必须填满整个时间段；
- 默认生成轻松、可执行的计划，不为了消耗剩余时间而调用高德补充外部地点；
- 默认形态为“1 个核心活动 + 最多 1 个辅助地点 + 交通与缓冲时间”；短时间窗口或用户明确要求时，可以只安排 1 个地点；
- 每次地点切换默认预留约 10–20 分钟弹性时间，计划结束前默认保留约 15–30 分钟；具体数值可根据路线、天气和场景调整，不作为必须填满的硬指标；
- 外部 Place 只有在满足用户明确意图或补足必要环节时才加入，例如用户明确要求“看展后吃饭”但收藏中没有合适餐厅；
- 支持“排满一点”“轻松一点”“只安排一个地方”“再加一家咖啡店”等自然语言调整，并保留本次规划的其他约束。

### 10.5 输出结构

系统生成：

- 1 个主方案；
- 最多 2 个备选方案。

微信默认只展开主方案，用户回复“看备选”后查看其他方案；Web/H5 最多并排比较 3 个方案。

每个方案必须包含：

- 时间线与各段预计时长；
- 单项与总费用区间；
- 交通方式、预计路程和关键换乘；
- 天气、地点状态及查询时间；
- 收藏来源或外部来源；
- 选择理由、排除原因和风险；
- 可继续使用的修改指令；
- 确认后将执行的动作。

#### 10.5.1 外部 Place 在计划草案中的交互

- 为补足局部缺口而检索到的外部 Place 可以直接进入计划草案，无需逐个进行前置确认；计划草案本身仍须由用户整体确认；
- 外部 Place 必须展示“高德补充 · 未收藏”标识，并提供“替换”“删除”“加入收藏”操作；
- 用户确认整份计划，只代表同意在本次计划中使用该地点，不等于将其加入收藏库；
- 只有用户明确执行“加入收藏”，外部 Place 才写入收藏库，同时保留高德来源信息；
- 同名分店、POI 匹配不确定或存在多个高概率候选时，不能直接进入草案，必须先让用户选择；
- 营业时间、价格等非必然返回字段缺失时，可以进入草案，但必须显示“待确认”和对应风险，不能由 Agent 补写；
- 微信使用文字或数字选项完成上述操作，Web/H5 使用按钮；两端调用同一业务动作，不维护两套数据字段。

### 10.6 计划修改与版本

- 用户可以说“少走一点”“晚两小时”“不要日料”等自然语言指令；
- Agent 保留未被修改的已确认条件；
- 重新计算后必须说明变化和被替换项；
- 已确认计划发生实质变化时生成新版本，并要求用户重新确认；
- 不静默覆盖已经确认的计划。

### 10.7 从收藏发起计划的状态流程

1. 用户通过自然语言或“帮我安排”快捷入口发起规划；
2. Agent 从输入中提取并向用户展示本次规划条件，包括空闲时间、活动范围、预算状态和其他明确要求；
3. 空闲时间或活动范围缺失时，只询问缺失的必要信息。预算、同行人、交通偏好和特殊要求均为可选，不得阻塞规划；
4. 条件齐备后，Agent 筛选已定位且符合硬约束的收藏，排除已结束 Event、待选择/待补充地点和无法按时到达的候选，并核验天气、路线及当前可获得的地点状态；
5. Agent 按 10.3.1 的规则判断是否需要高德补充外部 Place，随后生成 1 个主方案和最多 2 个备选；
6. 计划首先以“草案”状态返回，展示时间线、交通与缓冲、单项和总费用、收藏/外部来源、待确认信息、风险以及“确认计划”“调整”“查看备选”操作；
7. 用户使用自然语言修改时，Agent 保留所有未被修改的本次条件，重新计算并生成新草案版本；
8. 用户确认后，计划状态从“草案”变为“已确认”，生成高德路线入口和 `.ics` 文件；内部提醒必须单独获得用户授权；
9. 确认计划不自动收藏其中的外部 Place，也不自动执行购票、预订或其他外部写操作。

## 11. 动态核验与执行协助

### 11.1 三阶段核验

| 阶段 | 核验深度 | 目的 |
|---|---|---|
| 收藏阶段 | 轻量解析，记录来源和不确定项 | 快速保存，不追求一次性补齐全部事实 |
| 规划阶段 | 查询 POI、营业/活动状态、天气和路线 | 确保方案在当前条件下可执行 |
| 行前阶段 | 复核影响执行的关键变化 | 发现停业、天气或路线变化并提醒用户 |

价格和营业时间不保证能从地图获得。若来源缺失或相互冲突，保留各来源与查询时间，标记“待确认”，不凭空选一个结果。

### 11.2 计划确认后的动作

用户确认计划后，系统可以：

- 生成一个覆盖整段计划的 `.ics` 日历文件；
- 提供各段高德地图路线入口；
- 按用户选择创建内部提醒。

MVP 不直接写入 Google Calendar 或 Apple Calendar，不自动购票和预订。

#### 11.2.1 已确认计划的只读分享

1. 只有“已确认”计划可以生成分享链接；用户在计划详情查看分享预览并确认后，系统创建随机、不可枚举的只读 H5 链接；
2. 接收者无需登录，只能读取用户主动分享的这一份计划，不具备账号登录、编辑、评论、协作或访问其他数据的权限；
3. 默认展示计划日期、时间线、地点名称及公开地址、交通与缓冲、费用区间、天气/营业风险与最后查询时间、高德地点/路线入口和计划最后更新时间；
4. 默认隐藏用户姓名与微信身份、精确家庭/学校/工作起点、原始收藏来源链接、私人备注、完整收藏库、长期记忆、Agent 对话、授权记录和未入选候选；
5. 精确私人起点默认降级为区级或商圈级描述，例如“南山区出发”；
6. 分享页只展示最新“已确认版本”，草案修改不可见；新版本重新确认后同步更新分享页并标注更新时间，计划取消后显示“计划已取消”；
7. 用户可以随时关闭分享链接；链接默认在计划结束 7 天后失效；
8. 真实用户分享链接与作品集公开 Demo 使用不同数据和权限，Demo 不复用真实分享令牌。

### 11.3 权限分级

| 等级 | 示例 | 规则 |
|---|---|---|
| L0 本地只读 | 收藏、会话、记忆读取 | 可自动执行，记录访问范围 |
| L1 外部只读 | 网页、POI、天气、路线查询 | 可自动执行，展示来源和时间 |
| L2 内部可逆写入 | 自动收藏、计划草稿、`.ics` 文件 | 可执行，但必须提供修改、撤销或版本记录 |
| L3 长期或主动写入 | 长期记忆、主动提醒、外部消息 | 必须明确确认并保留授权记录 |
| L4 高风险动作 | 支付、下单、不可逆提交 | MVP 禁用 |

确认是单次授权。动作目标、时间或内容发生实质变化后，旧确认失效。

## 12. 主动计划、提醒与反馈

### 12.1 主动计划

- 默认关闭；
- 用户主动开启后，默认每周四 19:30 询问周末空闲时间；
- 只询问“什么时候有空、从哪里出发”，不直接生成或确认计划；
- 当周没有回复时不重复催促；
- 已存在确认计划时不再询问，只按用户设置发送行前提醒；
- 用户可随时修改时间或关闭。

示例：

> 周末快到了。你这周有空出去走走吗？可以直接回复：“周六下午，南山区出发，预算不限。”

### 12.2 行前提醒

- 默认采用单次授权：用户确认计划时选择是否开启，只对当前计划生效，不影响后续计划；
- 默认建议出发前 60 分钟，可修改，也可随时取消；
- 用户修改计划时间并确认新版本后，系统同步调整关联提醒，明确展示新的触发时间并允许取消；
- 用户取消或删除计划时，关联提醒自动取消；
- 发送前复核影响执行的关键动态信息。发现闭馆、天气或路线等变化时只提示风险并提供“重新规划”，不能静默修改已确认计划；
- 微信发送失败时在 Web/H5 保留真实的“发送失败/待查看”状态，不虚假显示已送达；
- 只有用户明确要求“以后每次确认计划后都提醒我”，才开启长期提醒偏好；长期设置可在“我的—提醒设置”中关闭；
- 长期提醒偏好只决定确认计划时是否默认创建提醒，每份计划的实际提醒时间仍须向用户展示。

### 12.3 活动反馈

反馈为可选能力，默认不泛化为长期偏好。作用包括：

- 确认计划是否真正发生；
- 将收藏更新为“去过”“部分完成”或继续保留；
- 记录未完成原因，区分计划问题、外部变化和用户临时取消；
- 为下一次计划提供候选优化依据；
- 在可能形成长期偏好时提出建议，由用户确认后写入。

单个地点的负面评价只进入地点反馈，不自动推断为全局偏好。

反馈能力分两级交付：

- **P0 手动完成反馈**：用户可在 Web/H5 或对话中主动标记“已完成 / 部分完成 / 未完成”，并更新计划与收藏状态；
- **P1 主动反馈询问**：系统在计划结束后按用户设置发起询问，记录未完成原因，并在必要时提出长期偏好建议。

没有主动提醒能力时，P0 手动反馈仍必须可用，以保证“收藏转行动”指标能够计算。

#### 12.3.1 完成反馈与状态更新

1. 用户选择“已完成”时，将计划标记为已完成，并将用户实际到访且已在收藏库中的地点更新为“去过”；
2. 用户选择“部分完成”时，必须继续让用户选择实际完成的计划地点。只有被选中的收藏更新为“去过”，其余收藏继续保留原状态；
3. 用户选择“未完成”时，将计划标记为未完成，不修改任何收藏状态；未完成原因可以选填，不得阻塞状态提交；
4. 对于高德补充且尚未收藏的地点，只更新对应 `PlanStop` 的执行状态，不自动创建收藏；可以在反馈后询问用户是否“加入收藏”；
5. 地点评价与计划完成状态分别保存。单次评价可以影响该地点后续排序，但不得直接泛化成长期偏好；
6. 只有用户明确确认“以后都这样推荐”等长期含义后，才将反馈建议写入长期记忆；
7. 用户可以在 Web/H5 或对话中更正误选的完成状态，更正后重新计算计划与地点状态，保留操作记录。

## 13. 记忆与上下文

### 13.1 记忆分类

| 类型 | 示例 | 生命周期 | 写入规则 |
|---|---|---|---|
| 显式长期偏好 | 喜欢展览；餐厅优先可预约 | 用户删除前持续 | 用户明确表达或确认后写入 |
| 推断偏好 | 可能偏好安静空间 | 待确认 | 必须展示依据并等待确认 |
| 临时约束 | 本周六 14:00–20:00 有空 | 指定日期或任务结束 | 自动过期，不转为长期偏好 |
| 动态事实 | 周六下雨；某馆今日闭馆 | 短期缓存 | 不写入长期记忆，使用时重新查询 |

#### 13.1.1 长期记忆写入判断

1. **明确记忆指令**：用户使用“记住”“以后”“每次都”等明确长期含义，例如“记住我不吃日料”，该表达本身视为写入授权。系统可以直接保存，随后告知“已记住”并提供修改、删除入口，无需重复确认；
2. **本次临时要求**：用户使用“这次”“今天”“本周”等限定表达，例如“这次不要日料”，只写入本次任务上下文或带过期时间的临时约束，任务结束后自动失效；
3. **含义不明确的评价**：例如“这家店太吵了”，先记录为地点反馈。Agent 若建议泛化为“以后优先安静地点”，必须展示建议并等待用户确认；
4. **行为推断偏好**：连续选择、删除或跳过某类地点只能作为提出记忆建议的依据，不能自动写入长期记忆；
5. **动态事实**：天气、临时闭馆、当前票价和单次排队时间只作为带来源和时间的动态事实使用，不写入长期记忆；
6. **敏感或精确位置**：家庭、学校、工作单位等精确地址不得自动记忆。MVP 只在用户明确授权后保存“南山区”“大学城附近”等完成规划所需的粗粒度常用区域；
7. 系统必须能够区分“用户明确表达的长期偏好”和“Agent 推断后经用户确认的长期偏好”，并保留各自来源。

### 13.2 记忆透明度

每条长期记忆记录：内容、类型、来源、创建时间、最后使用时间、确认状态和置信度。用户能够查看“为什么出现”“在哪次计划中使用”，并可以修改、删除或禁止某类记忆。

删除后的记忆立即退出检索，不再影响下一次计划。

### 13.3 会话控制

- 只加载与当前任务相关的记忆和收藏；
- 长对话可以摘要，但原始确认和授权记录必须保留；
- 临时任务状态与长期记忆分离；
- 外部工具结果先进行结构化校验，再交给模型生成回复；
- 前端和业务逻辑不直接解析模型自由文本，而使用结构化 Schema。

## 14. 端到端示例

### 14.1 收藏

周二，林晓把“深圳当代艺术与城市规划馆”的网页链接和一张咖啡店截图发给拾光。

Agent：

1. 解析链接，识别地点、行政区、类型、价格信息与来源；
2. 解析截图中的店名、区域和人均，对无法确认的营业时间标记“待规划前核验”；
3. 自动创建两条收藏；
4. 回复：“已收藏 2 条：深圳当代艺术与城市规划馆（福田区、免费、室内）和一家南山咖啡店（人均约 55 元，营业时间待确认）。回复 1 修改，回复 2 撤销最近一次收藏。”

林晓说：“咖啡店人均改成 60 元左右。”系统只修改共享数据模型中的价格字段，Web 端同步显示结果。

### 14.2 规划

周六上午，林晓说：

> 今天 14:00 到 20:30 有空，从南山地铁站附近出发，想去室内的地方，不设置预算。

Agent：

1. 将时间和出发地记录为本次临时约束；
2. 从收藏中检索深圳、室内且在时间内可达的候选；
3. 调用高德查询地点、路线和天气；
4. 发现某个展览当日需要预约，将其作为风险而非确定事实展示；
5. 生成一份主方案和两份备选；
6. 即使用户没有预算，也展示主方案预计总费用为 80–130 元。

主方案示例：

> 14:00 南山出发 → 15:00 深圳当代艺术与城市规划馆 → 17:30 福田咖啡店 → 19:00 返回。预计 80–130 元；地铁约 70 分钟；天气有雨，方案均为室内。展馆开放信息查询于 12:10，预约要求仍需在出发前确认。

### 14.3 修改、确认与执行

林晓回复：“咖啡店换成安静一点的，其他不变。”

Agent 保留时间、出发地和展馆，重新查询附近收藏，说明替换原因和费用变化。林晓回复“确认计划”后，系统：

- 生成一份 `.ics` 文件；
- 提供高德路线链接；
- 询问是否设置出发前 60 分钟提醒。

如果林晓随后要求改变出发时间，系统创建计划新版本，并再次请求确认。

### 14.4 反馈

活动结束后，林晓主动反馈：“咖啡店很安静，但展馆排队太久。”系统将两个地点更新为“去过”，记录地点反馈，并询问：

> 要记住“以后优先选择可预约、低排队风险的地点”吗？

只有林晓确认后，这条信息才成为长期偏好。

## 15. MVP 功能范围

### 15.1 优先级

- **P0**：形成核心闭环或保证安全所必需；
- **P1**：在核心闭环稳定后补齐，显著改善体验；
- **P2**：未来扩展，不进入首个可用版本。

### 15.2 功能需求

|---|---|---|---|---|

| FR-17 | 手动完成反馈 | 主动标记已完成、部分完成或未完成 | P0 | 更新计划/收藏状态，可计算行动转化 |
| FR-18 | 主动反馈询问 | 计划结束后询问结果、原因和地点评价 | P1 | 可关闭；偏好泛化前再次确认 |
| FR-19 | Agent 记录 | 展示输入、工具、结果、费用和授权 | P1 | 不暴露思维链、密钥与隐私参数 |
| FR-20 | 公开 Demo | 无登录深圳引导式沙盒体验 | P1 | 预置样例、约 10 轮操作、2 小时清理；不访问真实用户数据或执行外部写操作 |
| FR-21 | 计划分享 | 已确认计划生成可撤销的只读 H5 链接 | P1 | 默认脱敏、无账号权限，计划结束 7 天后失效 |
| FR-22 | 第三方预订 | 跳转票务或餐厅预订 | P2 | 首版不实现自动提交 |
| FR-23 | 连锁品牌收藏 | 用户可选择具体分店或明确收藏“任意分店” | P1 | 不批量制造收藏；规划时解析具体分店并保留来源与选择理由 |

## 16. Agent 工作机制

### 16.1 架构映射

1. **Channel Adapter**：将 Web 与 ClawBot 消息统一为 `InboundMessage`。
2. **Message Bus**：解耦用户消息、异步任务和回复。
3. **Agent Loop**：识别意图、加载最小上下文并驱动本轮任务。
4. **Agent Runner**：在受限循环中选择工具、读取结果并决定下一步。
5. **Tool Registry**：注册内容解析、收藏、地图、天气、日历和通知工具。
6. **Session Store**：保存短期会话与当前任务状态。
7. **Memory Store**：保存经确认的长期偏好和有时效的临时约束。
8. **Outbound Message**：转换成微信文本/图片/文件或 Web 卡片。

### 16.2 单轮处理流程

1. 判断意图：收藏、查询、规划、修改、确认、反馈或设置；
2. 只加载完成当前任务所需的会话、收藏与记忆；
3. 确定只读工具和可能的待确认动作；
4. 执行工具并校验结构化结果；
5. 对硬约束进行确定性校验；
6. 生成用户可读结果、来源、风险和下一步；
7. 仅按规则写入收藏、会话、计划或候选记忆。

### 16.3 模型职责边界

模型负责：

- 理解自然语言和意图；
- 从文本/截图中提取候选结构；
- 将用户表达映射为标准查询条件和标签；
- 组织计划说明与自然语言回复；
- 在允许范围内选择工具。

数据库与业务规则负责：

- 用户隔离、去重、状态流转和版本；
- 时间、预算、城市等硬约束校验；
- 写操作授权、幂等和审计；
- 任务重试、数据保留和删除。

### 16.4 可解释性

用户可查看：本次使用了哪些收藏、偏好与临时约束，调用了哪些工具，为什么排除候选，哪些事实仍待确认。

系统不展示：原始思维链、系统提示词、API 密钥、完整 Cookie/Token 和无关用户原文。

## 17. 数据模型与保留策略

### 17.1 逻辑实体

| 实体 | 关键字段 |
|---|---|
| User | user_id、渠道身份、默认计划城市、时区、通知与隐私设置 |
| Session | session_id、user_id、channel、摘要、状态、更新时间 |
| Message | role、content_type、content、附件、时间、trace_id |
| Source | source_id、URL、平台、抓取时间、截图、解析状态 |
| CollectionItem | item_id、Place/Event、标题、city_hint、位置、Event 有效日期、精确场次时间、时间线索、价格、标签、状态 |
| PoiReference | provider、poi_id、正式 city_code、坐标系、经纬度、match_status、候选 POI、匹配置信度、确认来源、最后核验时间 |
| Memory | memory_id、类型、内容、来源、有效期、确认状态 |
| Plan | plan_id、约束、方案、总时间、总费用、风险、状态、版本 |
| PlanItem | plan_id、collection_item_id/poi_id、时间、交通、费用 |
| AgentRun | trace_id、意图、模型、Token、费用、状态、耗时 |
| ToolRun | trace_id、tool、参数摘要、结果状态、耗时、错误码 |
| Approval | action_id、动作、目标、确认内容、状态、确认时间 |
| ScheduledJob | job_id、类型、run_at、状态、重试、幂等键 |
| Feedback | plan_id、完成状态、原因、地点评价、偏好建议 |
| ProductEvent | event_name、user_id/匿名会话、属性摘要、时间 |

Event 的“有效日期范围”和“精确场次时间”是两类独立事实：

- `event_start_date` / `event_end_date` 使用不带时区的自然日；结束日期包含当天，单日活动允许两端相等；
- `event_start_at` / `event_end_at` 只保存来源明确到钟点且带时区的准确场次，结束时刻必须晚于开始时刻；
- 只有展期日期的 Event 可以收藏和展示，但在准确到访时段核验前保持待补充，不能进入正式计划；
- 日期不得转换成午夜时间戳，也不得据此推断时区或每日开闭馆时间；无法可靠结构化的模糊表达继续保存为时间线索和不确定项。

### 17.2 数据隔离

- 所有真实用户业务查询必须以 `user_id` 强制过滤；
- 微信会话按“账号 + 渠道 + 对端用户”隔离；
- 公开 Demo 与真实用户使用独立数据库；
- Demo 只能访问虚拟深圳数据和临时沙盒数据；
- API 密钥、Token、Cookie 和精确隐私信息不得进入前端或公开仓库。

### 17.3 保留与删除

| 数据 | 默认保留 |
|---|---|
| 结构化收藏、计划、经确认的长期偏好 | 用户控制，直至删除或注销 |
| 原始截图 | 30 天 |
| 原始聊天消息 | 90 天 |
| 工具与模型运行日志 | 30 天 |
| 临时约束、精确临时位置 | 任务完成或有效期结束后清理 |
| 公开 Demo 上传文件 | 会话结束后尽快清理，最长不超过 24 小时 |

- 用户删除收藏或记忆后，立即从检索中隐藏；
- 后台在 7 天内完成物理删除；
- 恢复备份时必须重新执行删除记录，防止已删数据重新出现；
- 用户数据默认不用于模型训练；
- 用户注销时支持导出结构化数据并清除账户关联数据。

## 18. 外部 API 与工具

| 能力 | MVP 方案 | 用法 | 降级方式 |
|---|---|---|---|
| 大模型 | 阿里云百炼 Qwen3.7-Plus，非思考模式 | 意图、抽取、Tool Calling、规划与回复 | 保留条件并返回可恢复状态 |
| 网页解析 | `httpx` + `trafilatura`/BeautifulSoup | 公开页面正文和元数据 | 请求截图或文字补充 |
| 图片理解 | Qwen 多模态能力 | 截图 OCR 与结构化抽取 | 标记低置信字段并请求确认 |
| 地点/地理编码 | 高德 Web 服务 API | 收藏地点匹配；收藏不足时补充外部 Place；POI 搜索、详情、坐标 | 使用现有收藏并标注未核验，不伪造地点 |
| 动态活动发现 | MVP 不接外部数据源 | Event 只使用用户主动提交并保存的内容 | 提示继续添加收藏，或仅规划现有内容 |
| 路线 | 高德 Web 服务 API + URI | 步行、公交/地铁、驾车与打开路线 | 展示地址并提示手动导航 |
| 天气 | 高德天气 | 当前与短期天气核验 | 优先室内低风险方案并标记失败 |
| 日历 | iCalendar `.ics` | 确认后生成一个完整计划事件 | 提供可复制的时间地址文本 |
| 微信 | 腾讯 ClawBot/OpenClaw 微信插件 | 文字、图片、文件收发 | Web/H5 待办与查看入口 |
| 文件存储 | 本地私有目录 → 腾讯云 COS 私有桶 | 截图和导出文件 | 本地受控存储 |

### 18.1 模型规则

- 单一主模型，不做多模型路由；
- 模型名称、API Base 和密钥通过配置注入，不写死在代码中；
- 通过现有 OpenAI 兼容 Provider 接入阿里云百炼；
- 若后续成本或延迟评测不达标，再为截图解析增加 Qwen3-VL-Flash 等低成本模型；
- 模型结果必须通过 Pydantic Schema 与业务规则校验。

### 18.2 地图规则

- MVP 只使用高德，不接第二家地图或天气服务；
- 内部坐标统一记录供应商和坐标系，深圳首版使用高德 GCJ-02；
- 高德 POI ID 作为地点去重的重要依据；
- API 密钥只在服务端使用；
- 首版不强制嵌入交互式地图，使用服务端路线查询和高德 URI 打开路线；
- 价格、预约和营业时间不是高德必然提供的字段，缺失时必须明确标注。
- 高德外部检索只用于 Place，不将 POI 搜索结果推断成具体展览、市集、演出或讲座；
- 高德返回的是候选数据，偏好解释、约束校验与排序由拾光完成。

### 18.3 Provider 抽象

为 `ModelProvider`、`MapProvider`、`StorageProvider`、`JobQueue`、`TraceProvider` 和 `AnalyticsProvider` 定义接口。MVP 只实现一套默认 Provider，不为“可能替换”提前维护多套实现。

另预留 `EventDiscoveryProvider` 接口边界，用于未来接入活动平台或场馆官方数据源；MVP 不实现、不调用该接口，也不因此增加当前开发量。

## 19. 检索方案

### 19.1 MVP 检索

M1 起使用 PostgreSQL，不启用向量检索。候选查询采用：

- 城市、行政区、类型、状态、时间、价格等结构化字段；
- 标准标签匹配；
- 标题、地址、来源备注的关键词或模糊搜索；
- 高德距离和路线结果；
- 业务规则评分与排序。

模型将“周六下午想在南山看展，预算 200 元以内”转换为结构化 `SearchCriteria`，后端校验后生成 SQL，不让模型直接执行任意 SQL。

### 19.2 后续向量检索

当评测证明关键词与标准标签经常漏召回语义相近内容，或收藏规模显著增长时，在同一 PostgreSQL 中增加 `pgvector`。首版只预留接口，不引入独立向量数据库。

## 21. 后台任务与提醒

### 21.1 MVP 方案

使用 PostgreSQL 任务表 + 独立 Worker + APScheduler：

1. API 或周期触发器创建 `ScheduledJob`；
2. Worker 每 30–60 秒领取到期任务；
3. 使用数据库锁和幂等键防止重复执行；
4. 执行后记录结果、耗时和错误；
5. 失败最多自动重试 3 次，逐步延长间隔；
6. Web 通过 SSE 查看耗时任务进度。

创建主动提醒前必须确认。用户关闭主动计划、删除计划或修改时间时，关联任务同步取消或重新生成。

### 21.2 扩展边界

首版不使用 Redis 和 Celery。通过 `JobQueue` 接口隔离任务创建与执行；当出现大量并发任务、多个 Worker 节点、复杂优先级或明显任务积压时，再迁移到 Celery + Redis。

数据库时间统一存 UTC，用户展示使用 `Asia/Shanghai`。

## 22. 开发与部署

### 22.1 本地开发

- 使用 Docker Compose 统一 Mac 与 Windows 环境；
- 配置和磁盘更充足的 Windows 电脑可作为主开发机，建议使用 WSL2；
- 代码通过 Git 同步，不直接复制工作目录；
- 个人电脑不作为公网生产服务器。

### 22.2 公开部署

首选腾讯云香港轻量应用服务器：

- 参考配置：2 核 CPU、4 GB 内存、60 GB 以上磁盘；
- 不需要 GPU；
- Docker Compose 运行 Next.js、FastAPI、Worker、PostgreSQL、OpenClaw 微信网关和 Caddy；
- Caddy 负责 HTTPS 和反向代理；
- 腾讯云 COS 私有桶保存截图与导出文件，使用限时签名链接；
- Demo 与真实用户使用独立数据库和凭证；
- 数据库每日备份，保留最近 7 天；
- 初期手动部署，稳定后再增加 CI/CD。

选择香港节点是为了在作品集初期降低中国大陆服务器域名备案带来的上线等待。后续若需要稳定服务大量深圳用户，再评估大陆节点与合规备案。

### 22.3 微信适配技术 Spike

ClawBot 官方插件是 OpenClaw Channel Plugin，不能直接安装到 Nanobot。M2 开始前必须验证：

1. 微信文字 → Adapter → FastAPI/Nanobot → 微信文字回复；
2. 微信截图 → 下载/解密 → Nanobot 图片解析 → 收藏结果回复；
3. 用户、会话、消息 ID 与 `trace_id` 正确映射；
4. 断线重连、重复消息与发送失败能够恢复；
5. 登录凭证存放在持久化私有目录且不进入日志。

适配器只做身份和消息格式转换，不运行第二套拾光业务逻辑。

## 23. 可观测性、分析与成本

### 23.1 MVP 记录

首版在 PostgreSQL 中记录 `AgentRun`、`ToolRun`、`Approval` 与 `ProductEvent`，通过 `trace_id` 串联用户消息、模型调用、工具和最终回复。

用户侧 Agent 记录展示：

- 使用了哪些收藏、偏好和临时约束；
- 调用了哪些工具以及是否成功；
- 信息查询时间；
- 候选排除原因；
- Token、耗时和估算费用；
- 最终执行了哪些经确认的动作。

不记录或展示模型内部思维链、系统提示词、完整密钥、Cookie 和敏感原始参数。

### 23.2 产品事件

关键事件包括：

`onboarding_completed`、`content_submitted`、`content_parse_succeeded`、`collection_saved`、`collection_modified`、`collection_undone`、`memory_confirmed`、`plan_generated`、`plan_viewed`、`plan_adjusted`、`plan_confirmed`、`calendar_exported`、`route_opened`、`reminder_sent`、`activity_completed`、`activity_partially_completed`、`activity_not_completed`、`memory_deleted`、`tool_failed`。

### 23.3 成本与滥用控制

- 单次 Agent 任务最多 8 次工具调用、60 秒总时长；
- 单用户与全局每日模型费用上限均为可配置项；
- 每次模型调用记录模型、Token、耗时和估算费用；
- 网页、POI、路线和天气按有效期缓存；
- 公开 Demo 每位访客每天最多 5 次完整 Agent 任务；
- 达到额度后仍可查看预置案例；
- Demo 禁止外部写操作，限制上传文件大小并自动清理；
- 异常重复调用触发限流与熔断。

### 23.4 后续工具

首版不部署 PostHog 和 Langfuse。出现真实内测规模后可接入 PostHog；需要深入分析提示词、模型调用质量时可接入 Langfuse。两者通过预留的 Provider 接口接入。

## 24. 非功能需求

### 24.1 性能

- 普通文本请求应在 2 秒内返回处理状态；
- 完整文本回复目标 P95 ≤ 12 秒；
- 图片/网页解析目标 P95 ≤ 20 秒，超时后转后台任务；
- 收藏列表常用查询目标 P95 ≤ 500 毫秒；
- 超出 8 次工具调用或 60 秒时必须停止并降级。

### 24.2 可靠性

- 外部查询设置明确超时、有限重试和熔断；
- 写操作使用幂等键；
- 定时任务持久化，服务重启后可恢复；
- 用户修改条件后，失败任务不应覆盖新版本结果；
- 每条关键链路都可以通过 `trace_id` 追踪。

### 24.3 安全与隐私

- 密钥只存服务端环境变量或密钥管理系统；
- 日志默认脱敏渠道身份、精确位置、Token、Cookie 和敏感原文；
- 位置、长期记忆和主动通知均需按规则授权；
- 外部写操作记录确认文本、执行对象、时间和结果；
- 公开 Demo 与真实用户数据隔离；
- 文件下载使用限时签名链接，不公开对象存储桶。

## 25. 指标与验证

### 25.1 北极星指标

**每周由收藏转化为实际完成行动的条目数（Weekly Saved-to-Done Items）**。

该指标覆盖输入价值和行动价值，避免只追求消息量、收藏量或计划生成量。

### 25.2 核心漏斗

**完成首次收藏 → 查看结构化结果 → 发起计划 → 查看方案 → 确认计划 → 使用日历/路线/提醒 → 记录执行结果 → 再次使用**

### 25.3 个人项目验证

必须完成：

- 50 条内容解析测试样本；
- 其中至少 10 条为“仅店名”地点匹配样本，覆盖唯一结果、多个分店、重名地点和地图无结果；
- 解析结果按来源平台分别统计直接成功率、截图兜底成功率和最终失败率；
- 20 组深圳规划场景；
- 至少 2 周本人 Dogfooding；
- 硬约束违反数为 0；
- 记录字段修改率、工具成功率、端到端延迟、Token 与费用。

可选完成：

- 邀请 2–5 人进行可用性走查；
- 招募 10–20 位深圳用户完成 2 周内测。

如果无法找到内测用户，作品集必须明确说明“已验证功能与体验原型，尚未验证市场价值”，不得虚构用户数量、留存率和行为数据。

### 25.4 未来用户假设

以下指标仅在存在真实内测样本时评估，不作为个人项目完成门槛：

- 首次收藏完成率；
- 首次完整计划完成率；
- 7 日内重复收藏次数；
- 计划查看率与确认率；
- 收藏到行动转化率；
- 提醒关闭率与记忆纠正率；
- 次周留存。

### 25.5 竞品基准验证

桌面竞品分析后，M0/M1 阶段应尽量选择腾讯地图、Placify、Mindtrip 和 Google Maps 完成同任务对比；因地区、设备或账号限制无法使用的产品保留公开资料对照并明确说明。

统一测试任务：

1. 从一张包含深圳店名的截图保存地点；
2. 只输入一个存在多个分店的店名并完成消歧；
3. 保存 5 个地点后生成周六 14:00–20:00 的计划；
4. 将条件改为“少走路、不要日料”，检查其他约束是否保留；
5. 确认计划并进入路线、日历、分享或提醒。

统一记录：收藏步骤与耗时、正确 POI/分店匹配率、修改步骤、收藏复用情况、硬约束违反数、来源与不确定项展示、从计划到行动的步骤数，以及撤销/重新确认能力。

## 27. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 受限内容平台无法解析 | 收藏成功率下降 | 文本 URL 优先，失败立即转截图 |
| 截图字段识别错误 | 错误信息进入计划 | 置信度、字段来源、修改与行前复核 |
| 高德缺少价格/营业时间 | 计划事实不完整 | 保留来源，显示待确认，不编造 |
| 仅凭店名错误关联分店 | 路线与计划指向错误地点 | 匹配状态、候选消歧、用户纠正；未定位条目禁止进入正式计划 |
| ClawBot 与 Nanobot 不能直接安装 | 微信开发复杂度增加 | M2 前完成 Adapter 技术 Spike |
| 微信主动触达不稳定 | 提醒丢失 | Web 待办、重试和真实状态展示 |
| 模型违反硬约束 | 计划不可执行 | SQL/规则先过滤，生成后再校验 |
| 记忆误写 | 用户失去信任 | 推断偏好确认、来源可见、可删除 |
| 个人项目范围失控 | 无法形成可用版本 | 按 M0–M3 逐阶段交付 |
| 地图或 AI 平台复制单点功能 | 截图识别、AI 计划等卖点快速同质化 | 不竞争单点功能，持续强化收藏优先、约束可靠、透明控制和行动反馈闭环 |
| 无法招募内测用户 | 市场结论不足 | Dogfooding + 标准评测，诚实标注未验证 |
| 公开 Demo 被滥用 | API 费用增加 | 任务额度、限流、熔断和预置案例降级 |
| 隐私数据泄露 | 严重信任与安全问题 | 数据隔离、脱敏、私有存储和删除机制 |

## 28. 验收标准

### 28.1 功能验收

- 普通文字、文本 URL 和截图均能进入统一收藏流程；
- 各来源能够按兼容矩阵直接解析或进入截图兜底，不在失败页面反复空转；
- 用户能够修改或撤销自动收藏；
- Place/Event、来源、状态和不确定项能够正确保存；
- 仅店名输入能区分“已匹配、待选择、待补充”，多分店时不得擅自选择；
- 用户明确选择“任意分店”时只形成一条有效品牌级收藏，规划时解析具体分店且不产生重复 PlanItem；
- 未完成 POI 定位的收藏不得进入路线计算和正式计划；
- 时间和活动范围缺失时，Agent 只询问必要问题；
- 未提供预算时仍展示费用，不擅自使用默认预算；
- 计划能够生成 1 个主方案和最多 2 个备选；
- 用户修改一项条件后，其他已确认条件得到保留；
- 未确认时不得创建主动提醒或执行外部写操作；
- `.ics` 可被主流日历导入，高德链接打开正确地点；
- 用户可以手动标记计划为已完成、部分完成或未完成，并同步更新收藏状态；
- 删除记忆后，下一次计划不再使用该记忆；
- 关键任务拥有 `trace_id`、工具状态、费用和错误记录。

### 28.2 质量验收

- 50 条解析样本中，标题、地点和类型三项完全正确率目标 ≥ 90%；
- 20 组计划测试中硬约束违反数为 0；
- 核心流程测试成功率目标 ≥ 95%；
- 任务重试不产生重复收藏、计划、提醒或文件；
- Demo 与真实用户数据隔离；
- 日志、前端和公开仓库中不出现密钥、Token、Cookie 和精确隐私信息。

### 28.3 体验验收

- 新用户 3 分钟内完成首次收藏；
- 用户仅有 1 条收藏时也能获得单点价值；积累 3 条有效收藏后能被引导体验完整计划；
- 不接入微信时，Web/H5 仍能独立完成从输入到手动反馈的核心闭环；
- 微信每轮只提出完成当前任务所需的最少问题；
- 主方案能在一个移动端屏幕内看懂时间、费用、交通和主要风险；
- 用户能够区分 Agent 建议、实时事实和已执行动作；
- 复杂编辑能从微信顺利进入 H5，并看到同一条数据。

## 29. 已确认决策

以下事项在本轮评审中已确定，不再作为待决策项：

| 决策项 | 结论 |
|---|---|
| 产品名 | 暂用“拾光｜把收藏变成行动的个人生活 Agent” |
| 首发规划城市 | 深圳；收藏不限城市，其他城市暂不参与当前计划 |
| 收藏城市分类 | 收藏库按已确认城市分组/筛选；只有线索的条目进入“城市待确认”，界面后续设计 |
| 目标用户 | 在校大学生与年轻职场人共用同一套流程 |
| 规划输入 | 空闲时间与范围必填，预算可选 |
| 候选来源 | 收藏优先，外部推荐只在不足时补充并明确标记 |
| 外部检索边界 | Place 由高德补充；Event 在 MVP 不自动外部检索，仅预留后续数据源接口 |
| 外部检索触发 | 不按收藏条数判断；局部缺口可自动只读补充 Place，主要依赖外部地点时先征得同意 |
| 外部地点确认 | 可进入计划草案；确认计划不等于收藏，只有明确“加入收藏”才写入收藏库 |
| 连锁品牌收藏 | 未选分店保持待选择；用户明确接受任意分店后保存一条有效品牌级收藏，规划时再解析具体分店 |
| 计划密度 | 空闲时间是上限；默认 1 个核心活动 + 最多 1 个辅助地点并保留交通和缓冲，不为填满而外搜 |
| 计划生成流程 | 时间和活动范围必填；先生成可修改草案，确认后才生成路线与日历，提醒另行授权 |
| 完成反馈更新 | 已完成更新实际到访收藏；部分完成逐项选择；未完成不改收藏；未收藏外部地点只更新 PlanStop |
| 计划范围 | 同城、连续时间段、不超过一天 |
| 产品端 | Web/H5 先行，后接微信 ClawBot |
| Web/H5 主导航 | Agent 为默认首页；一级导航为 Agent、收藏、计划、我的 |
| 低保真原型 | 移动端 H5 优先制作 8 页，桌面端制作 2 个作品集关键页；异常和反馈作为页面状态 |
| 微信进入 Web | 使用 10 分钟单次登录链接兑换 30 天网页会话；支持设备撤销，不开发手机号密码与网页 OAuth |
| 计划分享 | 仅分享最新已确认版本；默认脱敏、只读、可撤销，并在计划结束 7 天后失效 |
| 公开 Demo | 深圳虚拟数据与内置样例；每会话约 10 轮 Agent 操作，2 小时自动清理，与真实用户数据隔离 |
| 输入 | 普通文字、文本 URL、截图 |
| 首次收藏流程 | 提交后显示识别中；结果分为已收藏、待选择、待补充和未收藏四种状态 |
| 编辑 | Web 按钮 + 微信自然语言/数字选项，复杂编辑进入 H5 |
| 记忆 | 长期偏好需确认，临时约束过期，动态事实不入记忆 |
| 记忆写入判断 | 明确“记住/以后”视为授权；本次要求临时使用；推断偏好须再次确认；精确敏感位置不自动保存 |
| 方案数量 | 1 个主方案 + 最多 2 个备选 |
| 主动计划 | 默认关闭；开启后默认周四 19:30 询问一次 |
| 行前提醒授权 | 默认每份计划单次授权并建议提前 60 分钟；明确要求后才长期默认开启，可随时取消 |
| 日历 | MVP 生成一个 `.ics` 完整计划事件 |
| 地图与天气 | 统一使用高德 |
| 模型 | 阿里云百炼 Qwen3.7-Plus，非思考模式 |
| 检索 | PostgreSQL 结构化检索；首版不启用 pgvector |
| 后台任务 | PostgreSQL Job + Worker + APScheduler，预留 Celery/Redis 接口 |
| 部署 | 本地 Docker；腾讯云香港轻量服务器公开部署 |
| 可观测性 | 自建 Agent/Tool/Approval/Event 记录，预留 PostHog/Langfuse |
| 商业模式 | 当前仅作品集，保留未来订阅假设 |
