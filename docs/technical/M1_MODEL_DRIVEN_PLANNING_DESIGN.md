## 1. 问题与目标

现有计划链路已经具备自然语言意图、收藏检索、高德事实、草案版本、确认、路线、日历和分享，但计划内容仍由确定性规则选取：候选最多 6 个、每项固定 60 分钟、每个方案最多 2 个地点。自然语言调整只修改整份 `PlanConstraints`，因此“再加一个公园”会把原方案重建成只包含公园的新版本。

本次目标是让模型负责计划语义：从可执行收藏与已授权的高德补充候选中生成地点组合、顺序和建议停留时长；唯一确定性规划器继续负责准确时间、路线和硬约束校验。不得新建第二套规划器或候选评分器。

## 2. 已确认的产品行为

### 2.1 两个入口，一条主链路

- Agent 自然语言是主入口。用户可以直接说“明天下午想看展、喝咖啡，晚上六点前结束”。
- 收藏页多选是辅助入口，用于指定优先或必须安排的收藏。
- 两个入口最终进入同一份计划请求、候选获取、模型提案、确定性排程、版本和确认链路。
- 没有精确出发点时先生成草稿；首段路线显示待补充，不伪造 `0 米 / 0 分钟`。确认或导航前再要求补充。

### 2.2 候选来源

1. 现有收藏服务只执行硬过滤：正式城市、状态、地点确认、Event 时间、明确范围、明确预算、明确排除和已知不可达事实。
2. 不新增计划前候选评分系统。个人收藏规模下将全部可执行候选交给模型；只有真实出现上下文或延迟问题后才增加有证据的上限。
3. 用户勾选项默认优先，不允许静默丢弃；用户可以单独标记为必须安排。
4. 必须安排项无法排入时返回冲突，不偷偷删除。

### 2.3 高德外部 Place 补充

- 能用收藏完成明确意图时不外搜，也不为填满空闲时间外搜。
- 有收藏核心但缺少用户明确要求的必要环节时，可以自动执行一次只读高德 Place 搜索。
- “有餐厅”不等于满足需求。超出明确范围、路线时间无法容纳、与固定 Event 冲突或明确类型不符的收藏不消除餐厅缺口。
- 没有可执行收藏或计划主要依赖外部 Place 时，先取得用户授权。
- `collection_only` 始终禁止外搜。
- Event 不通过高德 POI 搜索补充。
- 外部候选固定标注“高德补充 · 未收藏”，确认计划不会自动收藏。
- 复用唯一 `ExternalPlaceSupplementService`；删除只在“一个收藏 + include”时触发的狭窄旧判断，不另建推荐服务。

### 2.4 模型生成三个方案

- 模型一次返回 3 个方案。
- 第一个方案最符合用户原始要求和所选节奏，展示为主方案。
- 另外两个展示为备选，不预设“稳妥”“丰富”等固定风格。
- 每个方案引用已有候选身份，给出顺序、建议停留时长和简短理由。
- 模型不能虚构收藏、POI、路线、营业时间、价格或 Event 事实。
- 三个完全相同的方案无效；除此之外不规定差异策略。

### 2.5 唯一规划器负责可执行性

- 模型只提出候选组合、顺序和停留时长。
- 现有唯一 `PlanDraftService` 计算准确起止时间、交通时间和缓冲，并校验时间窗、Event、预算、已知营业冲突、路线和来源。
- 价格、天气、营业时间未知是风险提示，不是默认阻塞。
- 单个模型方案校验失败时不通过规则偷偷改写；保留其他合法方案并返回冲突原因。
- 不再固定每项一小时，也不再限制每个方案只能有一个核心和一个辅助地点。

## 3. 对话调整与版本

### 3.1 选择调整基础

- V1 首次包含一个主方案和两个备选。
- 每个方案均提供“基于此方案调整”和“确认使用”。
- 用户选择任意一个方案后，调整请求必须携带该方案身份；不能始终默认调整主方案。
- 确认请求同样携带方案序号。已确认方案序号写入现有 `draft_json`，日历、导航、分享和反馈统一读取它；旧数据默认读取主方案。无需增加数据库列或第二套执行表。

### 3.2 模型输出修改动作

模型读取被选方案、当前可执行候选、事实和用户指令，返回最小修改动作：

- 新增地点；
- 删除地点；
- 替换地点；
- 调整顺序；
- 调整停留时长；
- 修改时间、节奏或范围。

没有被动作涉及的原方案内容默认保留。“我还想去公园”必须表现为新增公园，而不是把 `include` 替换为仅有“公园”。

### 3.3 单线新版本

- 调整只生成被选方案的一个新版本，不重新生成三个方案。
- 新版本保留来源，例如“V2，基于 V1 备选 1”。
- 后续调整形成 V3、V4；旧版本不可变。
- 已确认 V2 后生成 V3，V2 继续作为当前有效计划；只有明确确认 V3 才替换。
- 日历、导航、分享和执行反馈只读取当前确认版本。

## 4. Event 缺失年份

- 截图或文本只出现 `7/1–8/28` 时，模型可以保留月日线索，但结构化年份保持为空。
- 不根据当前时间、发布时间或模型常识自动补当前年份。
- 页面显示“识别到 7 月 1 日至 8 月 28 日，年份待确认”。
- 用户选择年份后才形成完整 Event 日期并保存。
- 明确出现年份时按原确认流程处理。

Event 年份修复与计划生成代码独立，应使用独立提交和验收边界。

## 5. Web/H5 交互

- Agent 成功识别计划后显示计划生成进度，并在结果就绪后展示三个方案摘要；计划页提供完整时间线。
- 每个方案展示地点、停留、交通、费用、来源、风险、未安排项和原因。
- 计划页调整区明确显示“正在调整 V1 · 备选 1”。
- 调整完成后只展示一个新草稿和变更摘要。
- 当前已确认版本与待确认新草稿必须同时可辨认。
- 高德补充地点提供替换、删除和加入收藏操作。
- Agent 的“帮我安排时间”保留为自然语言入口，不降级成只跳转手动表单。

## 6. 必须删除的冲突旧路径

实施新行为时不得保留双轨兼容：

- `MAX_PLAN_FACT_CANDIDATES = 6` 的无条件截断；
- `_VISIT_SECONDS = 60 * 60` 的统一固定停留时长；
- `PlanDraftService` 的固定稳定排序生成方案；
- 每个方案最多两个 `PlanItem` 的限制；
- 把调整语义映射成整份 `include/exclude` 替换列表再重建计划的路径；
- 调整入口永远作用于当前版本主方案的隐含行为；
- 缺少起点时伪造首段距离或时间的 fallback；
- 与新模型提案边界重复的候选评分、解析或规划分支。

仍只保留一个 `ModelProvider`、一个 Agent 意图路由、一个收藏检索入口、一个 `ExternalPlaceSupplementService`、一个 `PlanDraftService` 和一个计划版本仓储。

## 7. 文档冲突处理

本设计是用户在 2026-08-11 明确确认的新产品要求，优先于旧文档中的以下描述：

- PRD 与核心流程中的“默认一个核心 + 最多一个辅助”；
- 技术方案中“模型只组织说明，确定性规则选择候选”；
- M0-5C 固定 60 分钟、最多两个地点和稳定排序的历史实现说明。

实施第一批修改时必须同步更新 PRD、核心流程、MVP 技术方案和状态文档，不能让新旧产品定义并存。

## 8. 非目标

- 不开始微信 ClawBot、M2、跨城或多日规划。
- 不新增向量数据库、推荐模型、通用工作流引擎或第二套 Agent。
- 不让模型直接调用数据库、高德或写入收藏。
- 不让高德搜索外部 Event。
- 不为罕见输入堆关键词、白名单和样本特例。

## 9. 验收主链路

1. Agent 自然语言创建长时间窗计划，三个方案均来自真实可执行候选，停留时长不再统一一小时。
2. 收藏多选继续进入同一生成链路，优先项和必须项语义正确。
3. “看展后吃饭”在附近无合适餐厅时按授权规则使用高德补充；范围外的已收藏餐厅不阻塞补充。
4. 缺少起点时先生成草稿，首段路线未知但不伪造；确认前补充起点后重新核验。
5. 从备选方案发起“再加一个公园”，新版本保留原地点并只新增公园。
6. 已确认版本在新草稿生成后仍有效，直到新草稿被确认。
7. 年份缺失截图不再保存模型猜测年份。
8. 新实现不存在固定一小时、固定两地点、整表 include 替换或第二套规划服务残留。
